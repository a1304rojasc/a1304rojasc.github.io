El usuario lo escribe el atacante: auditando Centinela

Centinela lee auth.log y decide a quién bloquear. Al auditarlo con mentalidad de atacante encontré 9 vulnerabilidades (2 altas, 4 medias, 3 bajas). Casi todas venían de la misma suposición equivocada.

La idea clave

En un log de SSH, el nombre de usuario es texto libre que elige el atacante al conectarse. Puede llevar espacios, la palabra from, IPs falsas, fórmulas de Excel o caracteres de control. Un detector que trata ese texto como si fuera de fiar se puede engañar con sus propios datos de entrada.

V1 · Alta · Culpar a una IP inocente (CWE-117)

El patrón original capturaba el usuario con \S+ y se quedaba con la primera IP de la línea. Si el atacante se conecta con el usuario x from 8.8.8.8 port 1, sshd escribe:

Failed password for invalid user x from 8.8.8.8 port 1 from 203.0.113.5 port 5555 ssh2
                                 └─ lo escribe el atacante ─┘ └─── lo escribe sshd ───┘

Centinela bloqueaba 8.8.8.8. El atacante escondía su IP y elegía a quién bloquear: una denegación de servicio contra terceros. Herramientas reales como fail2ban tuvieron fallos de este tipo.

Arreglo: anclar la regex al final de la línea. La IP buena es siempre la última from IP port N, la que escribe sshd.

V2 · Alta · Volverse invisible con un espacio

SSH permite usuarios con espacios (a b). Con \S+ la regex no encajaba y la línea entera se ignoraba: miles de intentos sin ningún aviso. El mismo arreglo de V1 (capturar el usuario con .+ y anclar el final) cierra los dos.

Cómo lo verifiqué

Cada hallazgo se reprodujo con una prueba real y tiene su test de regresión en tests/test_seguridad.py. Con el código anterior, 17 de los 19 tests de seguridad fallaban. Los otros 2 son de control. Con el código corregido pasan todos.

Lección: en cualquier herramienta defensiva, pregúntate qué partes de la entrada controla el atacante. Esas partes son las que hay que tratar como hostiles.
